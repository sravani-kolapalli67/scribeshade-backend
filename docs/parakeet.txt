💬 **Question**: Can you explain the Apache Spark architecture?

---
⭐️ **Answer**:  
- **Driver Program:**  
  - The central coordinator that manages the Spark application lifecycle.  
  - Converts user code into tasks and schedules them across the cluster.  
  - Maintains metadata, tracks job progress, and handles fault tolerance.  

- **Cluster Manager:**  
  - Allocates resources across applications. Examples: **YARN, Mesos, Kubernetes, or Spark’s standalone cluster manager**.  
  - Works with the driver to launch executors on worker nodes.  

- **Executors:**  
  - Distributed worker processes running on cluster nodes.  
  - Execute tasks assigned by the driver.  
  - Manage in-memory data storage (caching) and shuffle operations.  
  - Each executor runs multiple tasks concurrently, limited by the number of cores assigned.  

- **Tasks:**  
  - Smallest unit of work, representing a computation on a data partition.  
  - Tasks are grouped into stages based on shuffle boundaries.  

- **RDD/DataFrame/Dataset:**  
  - Core abstractions for data representation.  
  - RDDs are immutable distributed collections; DataFrames and Datasets provide optimized, higher-level APIs with Catalyst optimizer and Tungsten execution engine.  

- **Job Execution Flow:**  
  - User submits a Spark job → Driver creates DAG (Directed Acyclic Graph) → DAG is divided into stages → Tasks are scheduled on executors → Results are collected and returned.  

- **Fault Tolerance:**  
  - Achieved via lineage information in RDDs and task re-execution on failure.  

This architecture enables **distributed, in-memory, fault-tolerant processing** of large-scale data with high parallelism and scalability.

💬 **Question**: Can you explain SparkSession and SparkContext and their differences?

---
⭐️ **Answer**:  
- **SparkContext:**  
  - The original entry point for Spark functionality.  
  - Manages the connection to the cluster, job scheduling, and resource allocation.  
  - Used to create RDDs and coordinate distributed execution.  
  - In Spark 1.x and early 2.x versions, it was the primary API to interact with Spark.  

- **SparkSession:**  
  - Introduced in Spark 2.0 as a unified entry point.  
  - Encapsulates SparkContext, SQLContext, and HiveContext into a single object.  
  - Provides APIs for working with DataFrames, Datasets, and SQL queries.  
  - Simplifies configuration and session management for Spark applications.  

- **Key Differences:**  
  - SparkSession **replaces SparkContext** for most use cases, especially for structured data processing.  
  - SparkContext is still accessible via `spark.sparkContext` inside SparkSession.  
  - SparkSession supports higher-level APIs (DataFrame, Dataset), while SparkContext is lower-level (RDD-focused).  
  - SparkSession manages catalog, configuration, and SQL execution context, which SparkContext alone does not.  

This distinction is critical for modern Spark applications focusing on structured data and SQL workloads.

💬 **Question**: What is a broadcast join in Spark? Please explain.

---
⭐️ **Answer**:  
- **Broadcast Join:**  
  - A join strategy where the smaller dataset is **broadcasted (copied) to all executor nodes**.  
  - Avoids expensive **shuffle operations** by sending the small table to each executor, enabling a **map-side join**.  
  - Ideal when one table is **small enough to fit in executor memory** (typically under a few GBs).  
  - Significantly improves join performance by reducing network I/O and shuffle overhead.  

- **How it works:**  
  - Spark broadcasts the small dataset to all executors.  
  - Each executor joins the broadcasted data locally with its partition of the large dataset.  

- **Benefits:**  
  - Reduces shuffle and network traffic.  
  - Speeds up join execution, especially for large fact tables joined with small dimension tables.  
  - Helps mitigate data skew issues by avoiding shuffle on the small side.  

- **Trade-offs:**  
  - Requires enough memory on executors to hold the broadcasted dataset.  
  - Not suitable for large datasets that cannot fit in memory.  

- **Usage:**  
  - Can be triggered explicitly using `broadcast()` function in Spark SQL or DataFrame API.  
  - Spark’s cost-based optimizer can also automatically choose broadcast join if enabled (`spark.sql.autoBroadcastJoinThreshold`).  

This join strategy is a key optimization in large-scale Spark ETL pipelines to improve join efficiency and reduce job runtimes.

💬 **Question**: What are the challenges and implications of increasing the broadcast join size limit from the default (e.g., 10 MB) to a much larger size like 250 MB?

- Filtering only those groups where the count of consecutive years is greater than 1 (indicating consecutive wins).

- Use `ROW_NUMBER()` over partition by winner ordered by year.  
- Calculate `year - ROW_NUMBER()` as a grouping key for consecutive sequences.  
- Use `STRING_AGG` or `COLLECT_LIST` (depending on SQL dialect) to aggregate years.  
- Filter groups with count > 1 to get only consecutive wins.  

**Example SQL Query (Databricks / Spark SQL syntax):**  
```sql
WITH ranked AS (
  SELECT
    winner,
    year,
    ROW_NUMBER() OVER (PARTITION BY winner ORDER BY year) AS rn
  FROM IPL_winner_list
),
grouped AS (

),
consecutive_groups AS (

ORDER BY winner;
```

This query efficiently identifies and lists consecutive winning years per winner as requested.

⭐️ **Answer**:  
Here is a concise PySpark approach to identify consecutive IPL winners and aggregate their winning years:

- Use `Window` functions to assign row numbers partitioned by winner and ordered by year.

**PySpark Code:**  
```python
from pyspark.sql import functions as F
from pyspark.sql.window import Window

# Assume df is the DataFrame with columns: winner (string), year (int)

# Define window partitioned by winner, ordered by year
window_spec = Window.partitionBy("winner").orderBy("year")

# Add row_number column
df_ranked = df.withColumn("rn", F.row_number().over(window_spec))

# Calculate grouping key for consecutive years
df_grouped = df_ranked.withColumn("grp", F.col("year") - F.col("rn"))

# Aggregate years per winner and group
df_consecutive = (
    df_grouped.groupBy("winner", "grp")
    .agg(
        F.collect_list("year").alias("years"),
        F.count("*").alias("consecutive_count")
    )
    .filter(F.col("consecutive_count") > 1)
    .select("winner", "years")
    .orderBy("winner")
)

df_consecutive.show(truncate=False)
```

**Explanation:**  
- `row_number()` assigns sequential numbers per winner by year.  
- `year - rn` groups consecutive years together.  
- `collect_list` aggregates years into a list.  
- Filtering on count > 1 ensures only consecutive wins are shown.  

This PySpark solution efficiently identifies and lists consecutive IPL winning streaks per team.

- If a year breaks the sequence, the difference changes, creating a new group.  
- This technique effectively **clusters consecutive years together** without complex logic.  

This grouping key is the core trick to detect consecutive winning streaks efficiently in PySpark or SQL.

  - Returns records where "number" exists in both tables.
  - Common numbers: 1, 2, 3, 4, 5
  - table1 has duplicates for 1 and 3, so join is multiplicative:
    - 1 appears twice in table1 × twice in table2 = 2 × 1 = 2 rows (since table2 has only one '1')
    - 3 appears twice in table1 × once in table2 = 2 × 1 = 2 rows
    - 2, 4, 5 each appear once in both = 1 row each

    - 1: 2 rows  
    - 3: 2 rows  
    - 2, 4, 5: 1 row each

---
⭐️ **Answer**:  
- **INNER JOIN:**  
  - Returns only matching rows between tables.  
  - For duplicates, output rows = (count in table1) × (count in table2) for each matching value.  
  - Example: Number 1 appears twice in table1 and once in table2 → 2 × 1 = 2 rows.  
  - Total output is sum of such products for all matching numbers. In this case, 7 rows.

  - Returns all rows from table1, matched with table2 where possible.  
  - Duplicates in table1 remain as is.  
  - For matching values, each row in table1 joins with matching rows in table2.  
  - Unmatched rows in table1 appear with NULLs for table2 columns.

  - Returns all rows from table2, matched with table1 where possible.  
  - Duplicates in table2 remain as is.  
  - Matching rows multiply as per counts in both tables.  
  - Unmatched rows in table2 appear with NULLs for table1 columns.  
  - Total output rows = number of rows in table2 (6), but considering duplicates in table1 for matching values, total output is 8 rows.  

- **FULL JOIN:**  
  - Returns all rows from both tables, matched where possible.  
  - Includes all matched rows (like INNER JOIN) plus unmatched rows from both tables with NULLs on the missing side.  
  - Total output rows = matched rows + unmatched rows from table1 + unmatched rows from table2 = 9 rows here.  

**Key Points:**  
- Multiplicative effect of duplicates in join columns increases output rows.  
- LEFT and RIGHT JOIN output counts depend on the number of rows in the respective "all rows" table, but duplicates and matching counts affect actual output.  
- FULL JOIN combines unmatched rows from both sides, increasing output further.  

This detailed counting approach clarifies why LEFT JOIN output is not just the count of table1 rows but can be higher due to duplicates matching multiple rows in the other table.
